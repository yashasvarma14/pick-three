    How it works

    Started as my final project for Analytics for Unstructured Data (MSBA, UT Austin) and rebuilt since. No single chatbot answer here: thirteen small agents each check one thing, plain math does the ranking, and the LLMs are only allowed to interpret and explain.

    13agents
    ~25 sper search, most steps in parallel
    ~$0.006LLM cost per search
    43offline tests, every API faked
    1. 1PlanLLM planner picks the agents
    2. 2SearchGoogle Maps around you
    3. 3Scoreevery place, with plain math
    4. 4Checkfit, hours, live traffic
    5. 5Evidencereviews, websites, photos
    6. 6Rank & explainweights, then a write-up

    Statistics

    Review-adjusted ratings

    A 5.0 from 12 reviews shouldn't beat a 4.7 from 3,000. Every rating is shrunk toward the typical rating nearby with a Bayesian average, more strongly when there are few reviews.

    adjusted = (v·r + m·C) / (v + m)
    m = 40 prior reviews, C = median rating (capped at 4.4)

    NLP

    Matching by meaning, not keywords

    The request and every place are turned into sentence embeddings (all-MiniLM-L6-v2) and compared with cosine similarity, so "somewhere quiet to unwind" finds a tea house without sharing a word.

    sim(q, p) = q·p / (‖q‖ ‖p‖)
    min-max rescaled to 0.3–1.0 so it's comparable with the other scores

    Statistics

    Scoring every place found

    All 50–75 places Google returns get a quick weighted score; outdoor places are discounted by a rule-based weather suitability score from the forecast.

    0.45 fit + 0.25 quality + 0.20 proximity + 0.10 open
    × (1 − penaltyenv · (1 − weather)), penalty: outdoor 0.65, mixed 0.35

    Statistics

    Missing data, handled honestly

    No drive time? No website? That signal is dropped and the remaining weights are re-normalized, instead of quietly filling in a made-up 0.5.

    score = Σ wisi / Σ wi over the signals that exist
    w: fit 40, quality 25, travel 15, reviews 20, photo vibe 15

    RAG

    Evidence from reviews and websites

    Each finalist's Google reviews and own website are scraped, cut into 700-character chunks (120 overlap), embedded, and the closest chunks are retrieved. The LLM judges fit from those passages only, never from its own memory.

    coverage-aware top-k: best chunk per venue guaranteed, then up to 3 per venue

    Computer vision

    Photo vibe

    For requests where the look matters ("cozy", "date night"), a vision model rates each finalist's Google Maps photos for atmosphere. The planner skips it for "cheap tacos", since every photo costs money.

    photo_vibe ∈ [0, 1], 0.5 when the photos are unclear

    LLM engineering

    LLMs with guardrails

    The planner's plan is checked in Python against a dependency graph and a call budget. A validator removes places that only sound related. The write-up must return the exact ranking or it's rejected.

    plan → validate(deps, budget) · relevance ≥ 0.60 · order(write-up) == order(ranking)

    Data cleaning

    One business, one result

    Google lists some venues twice and chains have branches everywhere. Listings are merged by name tokens, website domain and haversine distance, then picked greedily with variety caps.

    same if (domain match ∨ tokens(a) ⊆ tokens(b)) ∧ distance < 0.1 mi

    Engineering

    Fast, and cheap to run

    Independent agents run concurrently, LLM checks fan out one call per venue, and a time-limited cache shares one request between simultaneous callers. Google calls back off with jitter on rate limits.

    repeat search: ~6 s instead of ~20 (cache) · 429 → wait 1, 2, 4, 8 s (+ jitter)
